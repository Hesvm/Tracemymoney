# App Audit Summary
*2026-05-24*

---

## Product Summary

**Trace My Money** is a personal finance tracker aimed at Iranian users who think in Toman and Iranian calendar (Shamsi). Users map their money flows on a visual canvas — income flowing into expenses, savings, and goals — and browse analytics per month. The app works fully offline and optionally syncs to Supabase when signed in.

Key product decisions: canvas-first, Shamsi-default, Toman/USD dual currency with locked historical rates, offline-first with cloud backup (not collaboration).

---

## Current Architecture

| Layer | Technology |
|---|---|
| Framework | Next.js 15.5.18, React 19, TypeScript 5.7, App Router |
| State | Zustand 5.0.2 (`useMoneyMapStore`, `useSyncStore`, `useAuthStore`) |
| Canvas | @xyflow/react 12.5.5 |
| Animations | Framer Motion 11.18.2 |
| Local persistence | Dexie 4.4.2 (IndexedDB) |
| Cloud sync | Supabase (storage object per user) |
| Auth | Supabase magic link (OTP) |
| Charts | @nivo/sankey + custom SVG (no other chart libs) |
| Exchange rates | Navasan API + IndexedDB cache by date |
| Styling | Tailwind CSS 3 |

**Single-page app.** `app/page.tsx` renders `MoneyMapApp`, which owns all modals and bootstrap logic.

**Canvas nodes:** 3 fixed system nodes (`node-income`, `node-expense`, `node-savings`) + user-created `goal` and `bucket` nodes. Nodes reference items via `itemIds[]`; items back-reference via `parentId`.

**Data model core types:**
- `MoneyItem` — id, type (income/expense/savings/goal/bucket), amount (`MoneyAmount`), date, recurrence, parentId
- `MoneyAmount` — amount, currency, `convertedAmountAtEntry?`, `exchangeRateAtEntry?`, `rateSource?`
- `MoneyFlowNode` / `MoneyFlowEdge` — @xyflow wrappers

**Persistence:** On every store mutation, `MoneyMapApp` serializes the full store to a `UserDocument` and saves it to IndexedDB (`documents` table, key `"local"`). Cloud upload is debounced 3 seconds after each mutation and fires immediately on `window.online` and `window.focus`.

**Sync strategy:** Whole-document Last-Write-Wins. On login, cloud and local are compared by `metadata.updatedAt` (= `lastModifiedAt` from Zustand). Newer document wins entirely.

**Analytics:** All 8 analytics cards (`MoneyFlow`, `Overview`, `RealValue`, `GoalsProgress`, `MoneyLeaks`, `IncomeRhythm`) receive a `AnalyticsSummary` derived from the current month's items only. Trend charts (6-month bars, 12-month area chart) use simulated multipliers applied to the current month's totals — not real per-month historical data.

## What Works

- **Canvas interactions** — drag nodes, pan, zoom, connect nodes, delete edges all work via @xyflow. Edge decoration (amount labels) is applied after connection.
- **Node creation** — quick-add flow creates the item, creates or reuses the matching node, auto-creates the edge from parent. Goal and bucket nodes are placed at defined offsets.
- **Month navigation** — navbar prev/next chips shift the selected ISO month; `isItemInMonth` correctly filters one-time items by date and recurring items from start date forward.
- **Recurring logic** — monthly/weekly/daily items appear in every future month from creation date. Yearly items match same month across years. No end-date support, which is fine for current use cases.
- **Quick-add flow** — type, amount, currency, date, note, recurrence can all be set. Amount gets locked with `convertedAmountAtEntry` at time of entry (for income/expense), keeping historical value intact.
- **Currency locking** — `createLockedAmount` stores `convertedAmountAtEntry` and `exchangeRateAtEntry` so past amounts don't recalculate when the rate changes today.
- **Exchange rate cache** — `saveDailyRate` writes each fetched rate to IndexedDB by date. `getHistoricalRate` looks up by exact date, falls back to the nearest prior date (`belowOrEqual`).
- **Settings modal** — currency toggle (TOMAN/USD), calendar toggle (shamsi/gregorian), canvas dots, soft animations, manual rate refresh, reset data, sign out.
- **Offline-first** — app loads fully from IndexedDB on launch; sync errors toast without breaking the app. `syncReady` gate prevents stale initial state from flushing to cloud before load completes.
- **Auth flow** — magic link sent, OTP confirmed, `syncOnLogin` merges data on first sign-in.
- **Visual style** — consistent soft neutral palette across all modals and cards. Framer Motion entry animations on all modals and analytics cards.
- **Analytics modal** — 8 cards cover income/expense flow, 12-month trend, inflation-adjusted value, goals progress, money leaks, income rhythm.

## Problems / Risks

### Critical

**1. Hardcoded API key in public bundle**
`lib/exchangeRate.ts` line 1:
```ts
const API_KEY = process.env.NEXT_PUBLIC_NAVASAN_API_KEY ?? "free4hjNTRd62AyJ6gzkIuuLQY8vZ4wz";
```
`NEXT_PUBLIC_` variables are inlined into the browser bundle. If the env var is missing (e.g., local dev, Vercel preview without secrets), the fallback key ships to the client in plaintext. Anyone can extract it from the minified bundle. Move the rate fetch to a Next.js API route so the key stays server-side.

**2. Whole-document LWW sync causes silent data loss on multi-device**
`lib/sync/mergeDocument.ts`: the entire document is replaced by whichever device has the newer `updatedAt`. If a user adds items on phone at 10:00 and on desktop at 10:01, the phone's items are gone with no warning and no recovery. This is acceptable for a single-device app but will become a real problem when cloud sync is marketed. The unimplemented plan `2026-05-22-offline-first-cloud-sync.md` acknowledges this — it needs to be executed before multi-device sync is encouraged.

**3. No Supabase RLS policies found**
No `.sql` migration files exist in the project. If the Supabase storage bucket or database tables lack Row-Level Security policies, any authenticated user could potentially read or overwrite another user's document by targeting their `userId` path. Verify RLS is configured in the Supabase dashboard and add migration files to the repo.

**4. `fallbackMonth = "2026-05"` in `lib/months.ts` will break new users**
`normalizeMonth` falls back to the hardcoded string `"2026-05"` when the store's `selectedMonth` is absent or invalid. From June 2026 onward, new users (or users whose store failed to hydrate) will land on the wrong month. Replace with `new Date()` derived current month.

---

### Important

**5. All analytics trend data is simulated, not real**
`lib/analytics.ts` — `deriveMonthlyIncome` and `deriveOverviewTrend` apply fixed multiplier arrays to the current month's totals. The resulting charts show smooth fabricated curves, not the user's actual history. This is a product-correctness issue: the charts look authoritative but are meaningless. To fix: store per-month aggregates, or pass all items (not just the current month's) to `getAnalyticsSummary` and group by month.

**6. Goals progress calculation is placeholder**
`deriveGoals` in `lib/analytics.ts`:
```ts
const saved = Math.min(target, savingsTotal * (0.42 / Math.max(goals.length, 1)));
```
This divides an arbitrary 42% of total savings across goals. It has no connection to real saving history. Same for `tomanGrowthPct: 40` and `usdGrowthPct: 6` hardcoded in `realValue`.

**7. `window.focus` upload on every tab switch**
`lib/sync/syncEngine.ts` — `registerOnlineListener` attaches a `focus` listener that calls `triggerUpload()` every time the tab regains focus, even if nothing changed. With IndexedDB writes on every keystroke already, this adds unnecessary Supabase storage writes. Gate it with a dirty flag.

**8. `FALLBACK_USD_TO_TOMAN = 94382` in `lib/analytics.ts` is stale**
This constant is used when `exchangeRate.usdToToman` is null. It was likely accurate when written but will drift. Use the most recently cached rate from IndexedDB instead of a hardcoded constant.

**9. `itemIds` on nodes duplicates `parentId` on items — two sources of truth**
`MoneyNodeData.itemIds[]` and `MoneyItem.parentId` both track the node↔item relationship. They can diverge (and `document.ts` has migration code that tries to reconcile them). A single source of truth (`parentId` on the item, derived `itemIds` on render) would eliminate the inconsistency risk.

**10. No item-level edit history / undo**
Users can delete or overwrite items with no undo. A mistaken "Reset Data" or accidental delete is unrecoverable if they haven't synced recently.

**11. No onboarding for new users**
`initialItems` in `lib/initialData.ts` seeds the canvas with demo data. This is fine as a first-run experience but there's no guidance on what the nodes mean or how to use the quick-add flow.

**12. Auth is magic link only**
No OAuth (Google, Apple). Magic link email delivery can be unreliable (spam filters, Supabase rate limits). Most users expect social login. Not critical but affects conversion.

### Nice to Have

**13. Two Shamsi abbreviation arrays**
`lib/months.ts` exports both:
- `shamsiMonthAbbreviations = ["FAR", "ORD", ...]` (used in navbar via `formatMonthLabel`)
- `shamsiMonthAbbr = ["Far", "Ord", ...]` (used in analytics via `formatShortDate` and `OverviewCard`)

Both are exported and used in different places. Consolidate to one array, use case transforms at the call site where needed.

**14. `bucket` node type is partially implemented**
`MoneyNodeType` includes `"bucket"` and the store creates bucket nodes, but there's no dedicated bucket analytics, no clear UX for what a bucket represents, and the `titleByType` just calls it `"Bucket"`.

**15. No tests for critical paths**
`lib/months.ts` `isItemInMonth`, `lib/sync/mergeDocument.ts`, `lib/currency.ts` `createLockedAmount`, and `lib/analytics.ts` have no unit tests. The `tests/` directory has only `monthSearch.test.ts`. Merge logic, recurring filtering, and currency conversion are the highest-risk areas.

**16. `useAnimatedRate` animates the exchange rate display but the number itself may be stale by hours**
Minor UX issue: the spinning number animation implies freshness, but the rate is only refetched on manual refresh or app load.

**17. 4 unimplemented plans in `docs/superpowers/plans/`**
- `2026-05-21-figma-connector-editing.md`
- `2026-05-22-offline-first-cloud-sync.md`
- `2026-05-23-historical-rate-lock.md`
- `2026-05-24-historical-exchange-rate-fallback.md`

These represent known gaps. Priority: cloud sync (critical for data integrity), historical rate lock (important for analytics accuracy).

## Suggested Next Steps

In priority order, staying within the existing product direction:

1. **Fix `fallbackMonth` to use current date** (`lib/months.ts`) — 15-minute fix, prevents silent wrong-month bugs for all new users from June 2026 onward.

2. **Move exchange rate API call to a server route** — eliminates the hardcoded key security issue. Create `app/api/exchange-rate/route.ts`, move `fetchUsdToTomanRate` there, call it from the store via `fetch("/api/exchange-rate")`.

3. **Implement the historical exchange rate fallback plan** (`2026-05-24-historical-exchange-rate-fallback.md`) — uses the IndexedDB rate cache when the API is unavailable, and stops using the hardcoded `FALLBACK_USD_TO_TOMAN` constant.

4. **Replace simulated analytics trend data with real per-month aggregation** — pass all items to `getAnalyticsSummary`, group by `item.date.slice(0,7)`, compute real monthly income/expense totals. This makes `IncomeRhythm` and `Overview` charts meaningful.

5. **Implement the offline-first cloud sync plan** (`2026-05-22-offline-first-cloud-sync.md`) — item-level merge before encouraging multi-device use.

6. **Verify and document Supabase RLS policies** — confirm storage bucket has user-scoped access rules, add SQL migration files to the repo so the security posture is reproducible.

7. **Gate `focus` sync upload with a dirty flag** — only upload on focus if `dirtyTimer` was set since last upload.

8. **Replace goals progress placeholder math** with real savings allocation logic tied to actual savings items with `targetAmount`.
